# Lattice 0.4.58

## 中文

### 重要修复

- 修复0.4.52–0.4.57检查到新版本后，真实Inno安装包可能因PE `ProductName`尾随空格而被旧更新器稳定拒绝的问题。
- 0.4.58安装包在签名前规范化该版本资源字段，因此旧客户端可以继续使用原有严格校验升级到0.4.58。
- 0.4.58及以后客户端会同时校验GitHub Release声明的文件大小、SHA-256摘要、PE四段版本和产品身份；损坏、截断、错误版本或错误产品的文件不会执行。
- 标准版与离线版继续使用确定的资产选择顺序；离线版不会回退到标准包。

### 安装包

| 变体 | 适用场景 | SHA-256 |
|---|---|---|
| `Lattice-Setup-0.4.58.exe` | 已安装Microsoft Visual C++ 2015–2022 x64运行库的普通Windows电脑 | `F2FF9FA12F6A5CBC7863BB9610A827C4AA812D3198730323FAEEE0F3BC053B20` |
| `Lattice-Setup-0.4.58-Offline.exe` | 内网、离线或缺少上述运行库的电脑；应用使用静态运行库 | `D1049F17AB18063235DCDF8E62508FCB7DC860A163C3CBA318EDF20082F397E0` |

两个`Latest`资产分别与对应版本化安装包逐字节相同。公开CER只含公钥，不含私钥。免费自签名便于内网管理员显式部署信任，但不等同于商业CA签名，也不保证陌生电脑不显示安全提示。

## English

### Important fix

- Fixes a deterministic update failure in 0.4.52–0.4.57 where the legacy updater rejected real Inno Setup packages whose PE `ProductName` contained trailing spaces.
- The 0.4.58 packages normalize that version-resource field before signing, so existing clients can upgrade to 0.4.58 using their original strict validation path.
- Starting with 0.4.58, the updater validates the GitHub Release size and SHA-256 digest, the exact four-part PE version, and the product identity before execution. Corrupted, truncated, wrong-version, or wrong-product files fail closed.
- Standard and offline asset selection remains deterministic; an offline build never falls back to the standard installer.

### Packages

| Variant | Use case | SHA-256 |
|---|---|---|
| `Lattice-Setup-0.4.58.exe` | Regular Windows systems with the Microsoft Visual C++ 2015–2022 x64 runtime installed | `F2FF9FA12F6A5CBC7863BB9610A827C4AA812D3198730323FAEEE0F3BC053B20` |
| `Lattice-Setup-0.4.58-Offline.exe` | Intranet/offline systems or systems without that runtime; the application uses the static runtime | `D1049F17AB18063235DCDF8E62508FCB7DC860A163C3CBA318EDF20082F397E0` |

Each `Latest` asset is byte-for-byte identical to its versioned counterpart. The public CER contains no private key. The free self-signed certificate supports explicit trust deployment by administrators, but it is not equivalent to a commercial CA signature and may still trigger security warnings on untrusted systems.
